## Key Topics & Concepts

This course works through the core data structures one module at a time, then applies them in two projects. Each of Modules Two through Five pairs a zyBook chapter with a coding assignment on that module's structure. Modules Three through Five also add a Project One milestone, and the two projects close out Modules Six and Seven. Topic summaries will be added as the course progresses.

* **Algorithms:** Module One, zyBook Chapters 1 and 2. Algorithms as ordered steps toward a task, and a first look at the course projects.
* **Vectors & Sorting:** Module Two, Chapter 3. Arrays, vectors, and linked lists weighed by operation speed, then the Vector Sorting assignment.

## Major Projects & Assignments

Alongside six graded sets of zyBooks participation activities, the graded work falls into the five groups below.

1. **Assignments: Vector Sorting, Linked Lists, Hash Tables, and Binary Search Tree**
    * **Focus:** Four coding assignments across Modules Two through Five, one per data structure, each paired with that module's zyBook chapter.
    * **Assignments:**
        * **Module 2, Vector Sorting:** A starter C++ console program loads bids from a municipal property-auction feed into a vector. Its menu loads, displays, and sorts them. The task is to implement selection sort and quicksort on the bid title, partition step included, and time each from `main()`. Two CSV files exercise the code, a small December 2016 set and a full set of 12,023 bids. On the full set, the sample output shows selection sort taking over ten seconds against a fraction of a second for quicksort. Submission pairs the source file with a short code reflection and pseudocode or flowchart.
        * **Module 3, Linked Lists:** The same bid data loads into a singly linked list and the menu searches it by bid ID. The starter again supplies the menu, parsing, and timing. The task fills in the LinkedList class: constructor, destructor, Append, Prepend, PrintList, Remove, Search, and Size. Append reaches the end through a tail pointer, so adding a bid is $O(1)$, while Search walks the whole list in $O(n)$. The reflection centers on keeping that tail pointer correct when Remove unlinks the last node or the only node.
        * **Module 4, Hash Tables:** Bids load into a hash table keyed on bid ID, with chaining for collisions over a prime bucket count. The task fills in the constructor, destructor, hash, Insert, PrintAll, Remove, and Search. Bucket heads sit by value in a vector, flagged unused by a sentinel key, so only chained nodes come from the heap. Remove splits into five cases because a head node cannot be deleted, only reset or overwritten by its successor. Beyond the stubs, the submission fixed four starter problems: a table created with new and never freed, a menu that looped forever on bad input, a declared but undefined Size, and copyable ownership of raw pointers. A separate test file, sanitizer builds, and the macOS leaks tool backed a submission note listing those changes.
        * **Module 5, Binary Search Tree:** Bids load into an unbalanced binary search tree keyed on bid ID. The task fills in thirteen stubs: constructor, destructor, Insert, Remove, Search, the three traversals, and their recursive helpers. One string comparison rule drives every operation, and equal IDs go right. The two repeated IDs in the full file therefore become their own nodes. Removal returns the node that takes the deleted node's place, so removing the root needs no special case. The submission added a post-order destroy helper, Size, and a bids-read count with error handling for a missing file. The Module Four menu and ownership fixes carried over. A test file with over a hundred checks and a fuzz run of random inserts and removes backed the submission note.

2. **Project One Milestones**
    * **Focus:** Three milestones in Modules Three through Five build toward Project One: the vector data structure, the hash table data structure, and tree data structure pseudocode.
    * **Milestones:**
        * **Milestone One, Vector (Module Three):** Pseudocode for the advising program on a vector. A Course object holds the number, title, and prerequisite list. A loader parses each line, validates it, and runs a second pass so a prerequisite defined later in the file still resolves. A linear search prints one course with its prerequisites, following the supplied vector example.
        * **Milestone Two, Hash Table (Module Four):** The same program on a chained hash table with a polynomial string hash over a prime table size. Insert rejects a duplicate course number. The load splits into two phases: phase one records every prerequisite reference by line number, and phase two checks each against the full table. Any failure clears the table, so a partial load never survives.
        * **Milestone Three, Tree (Module Five):** The same program on a binary search tree keyed on course number, duplicates rejected. A pending tree takes the load, and the catalog adopts it only after both phases pass. A failed reload therefore leaves the old catalog intact. Phase two also rejects a course that lists itself as a prerequisite.

3. **Project One**
    * **Focus:** Submitted in Module Six, after the three milestones. A pseudocode and runtime analysis document comparing a vector, a hash table, and a binary search tree for the advising program. It ends with a recommendation for Project Two.
    * **Approach:** Unified the three milestones behind six shared operations, so the loading, validation, lookup, and menu pseudocode appears once. Line-by-line cost charts cover both load phases for each structure, with each structure's Insert and Search cost plugged in. All three loads come out $O(n^2)$ in the worst case. The analysis therefore turns on expected cost, how realistic each worst case is, and the two advisor operations after loading. Memory and implementation effort get their own sections. Recommended the binary search tree, since its shape yields the ordered list without a sort and a logarithmic expected lookup. Noted that a sorted input file degrades it to the vector's cost, and that a self-balancing tree would remove that case.

4. **Project Two**
    * **Focus:** Submitted in Module Seven, the course's largest single deliverable. A working C++ course planner for the advisors, built on the Project One recommendation.
    * **Approach:** A single source file holds a binary search tree keyed on course number, a two-phase loader, and a three-option menu. Course numbers go in upper case so a lookup ignores case. The loader drops a self-reference, a number missing from the file, or a repeated prerequisite, with a line-numbered warning. The course still loads with the rest. The loader also handles Windows, old Mac, and Unix line endings, a byte order mark, stray whitespace, and a quoted file name. A failed reload keeps the previous data, and options two and three refuse to run before a load. A bash test runner compiles under clang and GCC with zero warnings allowed, then runs sixteen scripted cases and saves a transcript. The cases include a sanitizer build and an expect-driven interactive session that echoes input like a terminal. Submission notes list each departure from the sample output and the reason for it.

5. **Journal: Portfolio Submission**
    * **Focus:** The Module Eight journal, following the non-graded Portfolio Prep in Module Seven.
    * **Portfolio:** A private repository, as SNHU requires, holding the Project One analysis as Markdown and PDF, the Project Two source, and the course data file. Its README carries the reflection answers.
    * **Reflection:** Framed the problem as two advisor questions, which courses exist in order and what one course requires. Project One compared three structures on that data, and Project Two built the recommended tree. Described writing pseudocode before any C++, one structure per milestone, behind six shared operations and a two-phase load. Costing every statement showed that all three loads share a worst case, so expected cost and the advisor operations decided the choice. Two roadblocks got their own answers. A single-pass load would reject a course whose prerequisite appears later in the file. Recording line numbers in phase one and validating after the full read solved it. The course expects Visual Studio, while the work happens on Linux and macOS from the command line. A local clang++ build walks the program. A Forgejo Actions pipeline then builds the same source with the real MSVC compiler under Wine and checks expected output. Open rubric questions went to the instructor by email rather than to guesswork. On design growth, credited line-by-line costing with surfacing constants normally waved away, such as bucket heads allocated for an empty file. The analysis also changed one rule between projects: the pseudocode rejected a whole file on one bad prerequisite, and the C++ drops the reference with a warning instead. On maintainability, pointed to shared operations that made the catalog type a one-line swap. The C++ keeps the pseudocode's names, and its header lists every design decision in one place.

Named backend development, database design and query optimization, and performance analysis as the strongest skills. Pointed to rigorous complexity analysis as the skill most in need of improvement, the one this course targets. The intuition for which approach will run faster is already there. The mathematical vocabulary to prove it is the gap. For time management, described working ahead by finishing each module's work on the day it opens.     * **Algorithm:** Chose the morning school drop-off and wrote it as nine ordered steps, from the wake-up call to the drive back home. One step checked that the backpack held homework and lunch before leaving. Another waited in the drop-off line until reaching the front.

2. **Data Structures: Storing a Broadcast List**
    * **Focus:** Chose a scenario from work: the list of high school football broadcasts across North America on a Friday night. The list grows all week as games get scheduled, and reads outnumber edits by a wide margin. Users browse, page, and search by school or kickoff window, and cancellations are rare.
    * **Analysis:** Argued for the vector. Its dominant operations are all fast: amortized $O(1)$ appends, $O(1)$ indexing for pagination, and $O(\log \thinspace n)$ binary search over a kickoff-sorted list (Cormen et al., 2022). The linked list's advertised $O(1)$ insert and delete holds only with a pointer to the node in hand. Finding that node costs $O(n)$, and binary search is unavailable (Sedgewick & Wayne, 2011). Cited Stroustrup's run of Bentley's sorted insert-and-delete exercise, a workload the list should win. The vector still won by 50 to 100 times, because traversal and cache misses dominated (Stroustrup, 2012). A fixed array loses because the broadcast count grows every season. Noted that Knuth frames the same choice by which operations dominate (Knuth, 1997, Section 2.2). Attached a photo of the five-volume box set, also owned on Kindle.
    * **Takeaway:** Tied the choice to production, where the data lives in MySQL. MySQL's manual calls InnoDB indexes B-trees, and in practice they are B+ trees (Oracle, 2026a, 2026b). A kickoff-time lookup becomes a short tree walk and a scan of sorted leaves. That is the sorted vector and binary search applied to data too large for memory. Closed by asking peers to name an access pattern where the linked list would win.

3. **Coding Challenges: Telephone Numbers**
    * **Focus:** Took the optional thread with CodinGame's Telephone Numbers puzzle, rated medium. The input is $N$ phone numbers, and the output is how many trie nodes it takes to store them all. The site's example makes the idea plain: two numbers sharing their first ten digits cost eleven nodes, since the shared prefix is stored once (CodinGame, n.d.). A trie is a tree keyed by digit, so the puzzle lands on Module Five material. The approach is a node with ten child pointers and a counter. Insert follows an existing child for the next digit and creates one where it is missing, bumping the counter. The root stands for the empty string and goes uncounted, which the example confirms. A terminal flag would separate a stored number from a prefix of another. The puzzle asks only for the count, so it stayed out.
    * **Analysis:** Weighed the structure by what the trie gives up. Its lookup cost is $O(w)$ in the key length and never depends on how many keys are stored. The sorted vector and the binary search tree pay $O(\log \thinspace n)$ at best, and the tree degrades to $O(n)$ on sorted input. The linked list pays $O(n)$ for every search. The hash table matches the trie on whole-key lookup but has no order and no notion of a prefix. The trie enumerates its keys in order and answers prefix queries from its shape alone. The price is memory. For $N$ keys of average length $w$, an $R$-way trie holds between $RN$ and $RNw$ links (Sedgewick & Wayne, 2011). Most of those slots stay null. The fixes, a ternary search trie, a map per node, or a compressed radix tree, each trade simplicity for space. The algorithm is the trie's insert and nothing else, since search is the same walk without creation. Named deletion as the operation that produces the most wrong trie code, even though the puzzle never needs it. Delete clears the key's terminal flag, then prunes back up the path. A node goes only when it has no children and is not itself a terminal. Pruning too eagerly cuts a shared prefix from under a stored key, and skipping it leaks dead branches. Without parent pointers that means recursion returning whether the child emptied, the same shape as the Module Five removeNode.
    * **Takeaway:** The biggest hurdle was balancing the trie's simple design against its memory cost. Each node reserves ten child slots even when only one points anywhere. Shared prefixes cut the node count without touching the unused slots. The puzzle's node count and the program's real memory use were two different things to consider. Kept the array approach because the alphabet has ten digits and the numbers have a fixed maximum length. The care went into allocating a node only when the next digit's child was missing. That preserves the prefix savings and keeps the counter honest. Ownership works as in the tree: nodes come from insert, a post-order destroy frees them, and key length rather than $N$ bounds the recursion depth. That last point is the one real advantage over the binary search tree here. No insertion order can make the trie degenerate.

## Personal Reflection & Takeaways

I named the gap in my first post. After fourteen years of backend work, I could tell which approach would run faster. I could not prove it. This course gave me the vocabulary, and Project One made me use it. Costing every statement with a line cost and a count, before any code existed, is the discipline I lacked. It surfaced constants I would have waved away, such as a hash table paying for 179 bucket heads on an empty file. It also showed all three candidate structures loading in $O(n^2)$ in the worst case. The worst case alone picks nothing. Expected cost, how realistic each worst case is, and the operations that run after loading decide the choice. Knuth framed the same question by which operations dominate, and I now have the charts to answer it.

Choosing a structure got sharper too. The second discussion put a vector against a linked list on a workload the list should win. The vector won by a wide margin because cache misses dominate. Big O predicts the shape, and the hardware sets the constant. Project One showed the tree as the only structure whose shape yields the ordered list without a sort. The hash table has the fastest lookup and no order at all. The trie in the final discussion bounded lookup by key length rather than key count. The price is a pointer per symbol at every node. Each structure answered one question well, and the job is naming which question dominates.

The implementations were review in their mechanics and new in their discipline. The hash table and tree starters leaked their containers and looped forever on bad menu input. The menu output looked identical before and after those fixes. That taught me to verify memory cleanup on its own, with a leak tool and sanitizers, rather than trusting the screen. One shape kept returning. A recursive remove that hands back whatever now occupies its position unlinked the tree's nodes, and the same shape prunes a trie. Ownership questions followed every structure: who creates a node, who frees it, and how deep the recursion runs.

The projects also set my own bar. The rubric asked for a program that matched a sample session. I shipped one with a sixteen-case test runner, sanitizer builds, and a pipeline that builds the same source under real MSVC. A program that only works for one sequence of keystrokes is partly broken, and I did not want that in my portfolio. Where the sample output was wrong, such as a course list out of order, I documented the departure and kept the fix. Those are the habits I take forward: write the costs down, test past the sample, and leave the reasoning where the next reader can see it.
