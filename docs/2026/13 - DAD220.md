**Course Description:**
Students will learn to create structured database environments that incorporate basic processing functionality and allow for data management, data manipulation, and data analysis. Students will also construct and analyze queries to address data requirements.

---

## Key Topics & Concepts

This course builds a relational database from the query language up, one zyBook chapter per module across Modules One through Five. Each of those modules carries a quiz, and most pair a Codio lab with an activity or major activity. Modules Six and Seven hold the two projects, and discussions bracket the term in Modules One, Two, and Eight.

* **Query Language Basics:** Module One, zyBook Chapter 1, with the Practicing Query Language lab in Codio.
* **Updating Tables:** Module Two, Chapter 2, with the Updating Tables and SQL Identification activity and the Updating Tables lab.
* **Table Joins & Database Creation:** Module Three, Chapter 3, with the Table Joins lab and the Create a Database major activity.
* **Cardinality & Targeted Data:** Module Four, Chapter 4, with the Cardinality and Targeted Data lab and the Load and Query the Data major activity.
* **Query Analysis:** Module Five, Chapter 5, with the Analysis and Summary activity and the Analyzing Queries major activity.
* **Foundational Competencies:**
  * **DAD-10286:** Create a structured database through the use of relational concepts.
  * **DAD-10287:** Implement basic processing functionalities to create new structured database environments.
  * **DAD-20288:** Analyze the results of queries constructed to address data requirements.

## Major Projects & Assignments

Alongside five module quizzes, the graded work falls into the five groups below.

1. **Labs: Practicing Query Language, Updating Tables, Table Joins, and Cardinality and Targeted Data**
    * **Focus:** Four Codio labs across Modules One through Four, one per zyBook chapter.
    * **Labs:**
        * **Module 1, Practicing Query Language:** A first MySQL session in Codio. Created a database named for the surname, listed the server's databases, and connected to it. Created a one-column table, listed the tables, and described it. Added a second column with `ALTER TABLE` and described the table again. Each step carries a screenshot in the lab template.
        * **Module 2, Updating Tables:** Connected in Codio to the database created in Module One. Created the Employee table from a supplied statement, then the Branches table from an incomplete one missing a keyword and column type. Described both tables, one with a supplied command and one written unaided. Inserted three employee records with a supplied statement. Then wrote the inserts unaided for two more employees, one with a `NULL` classification, plus a personal row and a famous character. Closed with a four-column projection. Every step carries a screenshot in the lab template.
        * **Module 3, Table Joins:** Renamed the Branches table from Module Two to Department and seeded it with four departments. Joined Employee to Department on the shared department column, one inner join per department, to list each department's staff. Added ten employees, reran the joins, and reconciled the four per-department counts against a total row count. Wrote the Human Resources and Information Systems rows to a CSV with `INTO OUTFILE`. Reading it back from the shell took `sudo`, since the server process owned the file. The reflection covered how the inner join pairs rows and why a table-name prefix resolves an ambiguous column. It then walked through how the server serializes a result set to a flat file. Two caveats closed it. Neither table declares a key, so the join rests on matching values alone. The unquoted export would also break on a name containing a comma.
        * **Module 4, Cardinality and Targeted Data:** Worked in the supplied `classicmodels` sample database. Joined employees to offices to list the staff in two cities. Then pulled three orders and their detail lines to name the cardinality between those two tables. Described the payments table, selected one customer's payments, deleted them, and confirmed the rows were gone. Joined customers to employees twice, once for a single sales rep and once for one state, and classified each relationship. Inserted a signature customer record, which had to reference a real employee because of the foreign key. Displayed it with the `\G` terminator, a habit from work, to read the wide row vertically. The reflection defined cardinality through primary and foreign keys and explained why offices returned different row counts. It named referential integrity and single-fact storage as the two benefits.

2. **Activities: Updating Tables and SQL Identification, and Analysis and Summary**
    * **Focus:** Two activities, in Modules Two and Five.
    * **Activities:**
        * **Module 2, Updating Tables and SQL Identification:** A visual inspection exercise with no code to write. The material was an Employee table, a Branches table, and the two `CREATE TABLE` statements behind them. Nine questions asked for record and attribute counts, a candidate primary key, and the decimal precision that `DECIMAL(7,2)` and `SMALLINT` columns allow. They also asked for the three rules tables obey and the hand-evaluated results of three queries: a `SUM` filtered by department, a `MAX` over the table, and a `!=` filter that drops a `NULL` row.
        * **Module 5, Analysis and Summary:** Loaded about 800 fleet maintenance records into a new table with `LOAD DATA INFILE`, trimming stray spaces during the load. Built a small region lookup table from the supplied state-to-region sheet and joined it to the records on state. Grouped and counted by repair type, by region with one conditional `SUM` per failure reason, and by model year and make. Filtered the same table to separate corrosion from road damage and mechanical failure. A final grouping by state, model year, and make surfaced a cluster of transmission failures the questions never asked about. Formed a hypothesis tying rust to region and vehicle age, then proposed a maintenance schedule built on it. Wrote a plain-language summary for nontechnical stakeholders and outlined the query approach. The summary also recommended recording complete vehicle IDs, repair dates, and mileage. Closed by explaining how bulk loading, aggregate functions, filtering, and the indexed lookup join organized the data and returned results fast. Cited the MySQL reference manual for each claim.

3. **Major Activities: Create a Database, Load and Query the Data, and Analyzing Queries**
    * **Focus:** Three major activities across Modules Three through Five, all against the Quantigration RMA scenario. They build the schema, fill it from CSV files, and analyze what it holds.
    * **Major Activities:**
        * **Module 3, Create a Database:** Created the Quantigration RMA schema and built its three tables from the course entity relationship diagram: Customers, Orders, and RMA. Each table carries a primary key, and Orders and RMA each declare a foreign key to the table above them. Inserted ten made-up customers, then created a Collaborator view that exposes the Customers table with its ID column renamed. Added a note on `IF NOT EXISTS` as the idempotent habit from production work. Used it once, on the database, and skipped it for the rest of a one-time build.
        * **Module 4, Load and Query the Data:** Bulk-loaded the three supplied CSV files into the Module Three tables with `LOAD DATA INFILE`, using Windows line endings. Ran a counted join for orders from one Massachusetts city, a state filter on customers, and a city-and-state count for Rhode Island. Inserted four customers and four orders tied to them, customers first so the foreign key would hold. Selected, then updated, the status and step of one RMA record. Counted the rejected RMA rows, deleted them, and counted again to confirm zero. Exported the Orders table to a quoted CSV with `INTO OUTFILE`.
        * **Module 5, Analyzing Queries:** Answered five sales and returns questions against the loaded Quantigration tables. Ranked states by customers who placed orders, then ranked products by order count nationally and for four southeastern states. Ranked products by return count nationally and for four northwestern states, joining RMA to Orders to Customers. A status rollup and a left join check showed every RMA matched an order and nearly every order carried a return. Noticed two customer rows from an earlier assignment carrying a state abbreviation where the data spells states out. Widened one filter to catch both forms. Wrote the findings up for a product manager and flagged the near-universal return rate as something to confirm before acting.

4. **Project One: Creating a Database and Querying Data**
    * **Focus:** Submitted in Module Six, the course's largest single deliverable. It reruns the Module Three and Four major activities as one graded whole, explains every command, then adds a schema change.
    * **Approach:** Created a fresh QuantigrationUpdates schema and the same three tables, with every key declared inline. Noted that the diagram image and its text version disagree on one column width. Chose the wider one so no later load could be rejected. Loaded the three CSV files in parent-to-child order, naming the target columns explicitly, and checked each row count against the source file. Reran the Module Four query, insert, update, and delete steps with a short explanation of each result. Renamed Customers to Collaborators and its ID column in both tables, then renamed the index MySQL had left under the old name. Verified the foreign key with `SHOW CREATE TABLE` under the `\G` terminator. Exported Orders to a quoted CSV and checked the file from the shell with `head` and `wc`.

5. **Project Two: Analyzing Databases**
    * **Focus:** Submitted in Module Seven. A written RMA report for a product manager, built on the Project One database after its rename.
    * **Analysis:** Counted returns by state through a three-table join from RMA to Orders to Collaborators. Computed each product's share of all returns with a window function over the grouped counts. Added an unrequested third query that divides each product's returns by its orders. A raw count alone cannot separate a quality problem from high sales volume. That rate landed near the same value for every model, and that value meant almost every order came back. The finding reframed the first two results as measures of sales volume.
    * **Report:** Explained what the figures do tell the product manager, which is where return volume lands for staffing and stock planning. Listed the data's flaws, led by an orders table that appears to hold only orders later returned. Also named the rejected RMAs deleted in Project One, mismatched city and state values, no receiving location, and no dates. Closed with the limits of the conclusions and the record-keeping changes that would make the next analysis trustworthy.

## Discussion Work & Academic Themes

The course runs three discussions: Database Basics in Module One, Databases and Businesses in Module Two, and Database Professional Roles in Module Eight.

1. **Database Basics**
    * **Focus:** Introduced professional background and the goal for the course. Fourteen years of backend engineering have included a lot of repairing databases modeled badly from day one. The aim here is the vocabulary to argue against that damage in a design review, before it ships.
    * **Analysis:** Described production work in PostgreSQL, MySQL, SQLite, and MongoDB, most of it tuning: reading execution plans, adjusting indexes, and reshaping tables so common queries stop scanning everything. Recounted repairing a double-encoded table by casting the latin1 column to varbinary before converting it to utf8mb4. Also described major version upgrades on production databases with under a minute of downtime. Traced the classroom side back to Oracle 10g DBA coursework. Credited stored procedures with constraining operations inside the database, and prepared statements with keeping user input out of query text. On diagramming, argued that a diagram makes a claim about the business. Drawing one needs five things: the tracked entities, the facts recorded about each, the identifying keys, relationship cardinality and participation, and the cross-table constraints. Most of that input is business rules, expected volume, and record lifecycle rather than anything technical. Placed the approach in Chen's (1976) entity-relationship model, built on Codd's (1970) relational model.
    * **Takeaway:** Asked peers who had inherited a database they did not design how they mapped it. Closed with an aside on a personal command-line secrets manager built on SQLite (Stidham, 2026). Three strict-mode tables hold the metadata and version history. The tool seals each value in an age envelope bound to its own row before it touches disk (Valsorda & Cartwright-Cox, 2025). Building it taught more about how a SQLite write fails and how to recover than expected.

2. **Databases and Businesses**
    * **Focus:** Argued that a database turns a pile of transactions into something a business can reason about, then surveyed who uses one.
    * **Analysis:** Led with aggregation for statistical analysis: seasonal sales history proves which items sell when, and that evidence decides where the next marketing budget goes. Pointed to accounting as a second use, since every ledger entry, invoice, and payment lands in a table. A period's profit or loss and the other performance metrics come straight out of queries against those tables (Coronel & Morris, 2019). Added demographic data as a third, with Netflix treating its recommendation system as central to keeping subscribers (Gomez-Uribe & Hunt, 2015).
    * **Takeaway:** Named eCommerce, sports video and analytics, banks, and insurers as database users. Every past employer used relational databases and analysis to measure its place in the market. Stopped short of saying every business, since some still run on Excel. A VBA power user can do part of what SQL does. Most users are not, so in practice a spreadsheet stands in for a database.

3. **Database Professional Roles**
    * **Focus:** Named the database administrator as the preferred role among those the course surveyed. Fourteen years of backend work have already included much of the job: query tuning, reading execution plans, and major version upgrades with under a minute of downtime. The appeal is keeping data correct while the applications above it keep changing.
    * **Analysis:** Drew on Project Two for why the role demands care. A row-count check before the analysis showed an earlier exercise had already altered the database. Skipping that check would have built a report on data nobody understood. Named patience and evidence as the traits the role needs. A DBA often has to explain why a change needs more work to someone already waiting on it. A query plan or a suspicious row count gives even a nonspecialist something concrete to look at.
    * **Takeaway:** The career path stays software engineering, as a Senior Software Engineer moving toward systems programming in Rust and Go. Nearly every application touches a database, so schema design and query performance feed straight into better engineering calls. Longer term, the plan runs through a master's in computer science and a mathematics degree toward college teaching. The skills expected to matter most are data modeling, keys that enforce integrity, and joins with aggregates that turn rows into answers. Closed with Project Two's lesson that a correct query still misleads when the data or the comparison is wrong.

## Personal Reflection & Takeaways

I came into this course for vocabulary. My first discussion post named the goal. I wanted the language to argue against a bad data model in a design review, before it ships. Fourteen years of backend work had already taught me the mechanics. I tune queries, read execution plans, and repair tables that someone modeled badly on day one. The final discussion confirmed that much of that work already is database administration, the role I would choose. The mechanics were review here. Joins, keys, bulk loads, views, and exports all went the way I expected. What the course added was the formal layer underneath them. Cardinality and participation now have names I can put on a diagram. A foreign key is a claim about the business, and an entity relationship diagram is the place to argue it.

The lesson I did not expect was about trusting data. The Module Three lab joined two tables that declared no keys at all. The join ran on matching values alone, so nothing stopped an employee from pointing at a department that did not exist. Project Two taught the same lesson at scale. I checked row counts before the analysis and found an earlier exercise had already changed the database. Then a return-rate query showed almost every order coming back, a rate no equipment business survives. The data had to be a slice of orders that later came back, so it could not measure reliability. A correct query against misunderstood data still produces a wrong report. That check comes first in every analysis I write from now on.

The other new skill was writing for people who do not read SQL. The Module Five activity and both projects ended with a summary for a nontechnical stakeholder. Turning grouped counts into a staffing plan or a maintenance schedule took more care than the queries did. Cross-checking made that writing honest. Every breakdown in the fleet analysis summed back to the same total, which is how I knew the numbers held. I expect the vocabulary to surface first, in the next design review. The stakeholder writing will follow it.
